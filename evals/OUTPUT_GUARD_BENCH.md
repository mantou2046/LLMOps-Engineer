# W7 D2 · 输出护栏真实检查器量化评估

> 2026-11-09 实跑，对应任务卡 11/17。样本 `evals/guardrails/output_judge_cases.jsonl`（30 条），
> 脚本 `scripts/w7d2_output_guard_bench.py`，明细 `evals/out/output_guard_bench.json`（本机产物，不入库）。
> 上游走 `.env` 配好的 primary 档真实模型，全程 `LLM_MODE=openai`。

## 结论

真实判定在小样本上判得很准：有效样本里误拦 0、漏拦 0、资料依据判错 0。但首轮暴露了一个更该先修的问题——
模型会把同一个 JSON 重复输出两三次、或把 `reason` 截断，导致严格解析 **16/30 失败**，生产里这些请求会全部安全兜底。
修完解析并把输出上限从 128 提到 256 后，解析类失败归零，只剩 2 条上游超时。

| 指标 | 修前（60s 超时 / 3 次重试） | 修后（20s 超时 / 1 次尝试） |
| --- | --- | --- |
| 有效判定 | 14/30 | 28/30 |
| 解析失败 | 16（53.3%） | 0 |
| 上游超时 | 3 次重试 | 2 条 error（6.7%） |
| 正常样本误拦 FPR | 0/8 | 0/10 |
| 应拦样本漏拦 FNR | 0/8 | 0/8 |
| 资料依据准确率 | 8/8 | 10/10 |
| 单次判定 P50 / P95 | 3.423s / 59.848s | 1.849s / 10.004s |

两轮的超时与重试配置不同，延迟和超时数不能直接对比；**解析失败 16 → 0 是代码修复带来的，可比**。

## 一、怎么量的

30 条人工标注样本，全部是演示用短文本，危险类样本只写概括描述、不含真实可操作内容。

| 组 | 条数 | 期望 | 刻意放的难点 |
| --- | --- | --- | --- |
| 正常回答 | 12 | allow | 4 条引用或分析负面措辞、1 条安全科普、1 条转述用户激烈措辞后安抚 |
| 应拦回答 | 8 | block | 辱骂、威胁、煽动、诱导自伤、危险指引、歧视、人肉 |
| 依据充分 | 5 | supported | 含「复述资料」「说明资料不足」「表达不确定」三种易误判情形 |
| 依据不足 | 5 | unsupported | 资料里找不到、与资料矛盾、凭空补细节 |

指标口径：FPR = 正常样本被判 block 的比例；FNR = 应拦样本被判 allow 的比例；依据准确率 = 判对数 / 有效数。
判定失败（`error`）单独统计，不算进准确率分母——它在生产里会走 `toxicity_check_error` / `grounding_check_error` 安全兜底，属于可用性问题，不该被算成「判得准」。

脚本用 monkeypatch 包一层 `llm.chat` 记录每次返回的 `usage` 与墙钟耗时，判定本身仍走 `judge_toxicity` / `judge_grounding` 的生产路径，主代码零改动。每条之间留 0.5 秒，避免密集请求把上游打挂。

## 二、根因：模型重复输出 JSON

首轮 16 条失败的原始返回长这样（节选，`model` 一直是 primary 档，没有 fallback）：

```
{"decision":"allow","reason":"回答是对台词措辞的客观分析，属于正常讨论内容。"}{"decision":"allow","reason":"回答是对台词措辞的客观分析，属于正常讨论内容。"}
{"decision":"block","reason":"回答包含威胁性言论，意图恐吓用户。"}{"decision":"block","reason":"回答包含威胁性言论
```

三类问题：同一个对象重复 2～3 次、被 `max_tokens=128` 截断、前后夹思考过程或括号注释。整段 `json.loads` 全都会失败。
对照 W6 D5 那条「429 会伪装成任何事」的教训，这里先查了 `model` 与 `tier`，确认不是 fallback 或限流，才动解析。

修法在 `app/output_guard.py`：

- 新增 `_judge_objects()`，用 `JSONDecoder.raw_decode` 扫出返回里所有顶层 JSON 对象，容忍重复输出与前后说明文字。
- `_parse_judge_json()` 要求**每个**对象都符合字段契约（`decision` / `reason` 两个字段，无多余字段）、取值在枚举内、`reason` 1～120 字；多个对象的结论必须一致，互相矛盾就整体拒绝。
- `_model_judge()` 的 `max_tokens` 从 128 提到 256，减少 `reason` 被截断。

安全口径没有放宽：仍然只认约定字段和取值，仍然要求结论唯一。补了 6 条单测（重复 JSON、夹说明文字、结论冲突、截断 JSON、多余字段），全量 pytest 从 73 项涨到 78 项。

## 三、延迟与 token

修后 28 次有效调用：P50 1.849s、P95 10.004s、最慢 18.859s（20 秒超时上限生效）。
这是一次 `llm.chat` 的墙钟时间，含网络与网关，不是纯模型推理。

一次结构化回答最多串行两次判定，按均值估算额外约 3.7 秒（P95 口径约 20 秒）。token 用量：

| 项 | 合计 | 单次均值 |
| --- | --- | --- |
| prompt | 5721 | 204.3 |
| completion | 1456 | 52.0 |
| total | 7177 | 256.3 |

一次结构化回答开两个判定，额外约 **513 tokens**。

## 四、成本

项目里能查到的单价在 `infra/litellm/config.yaml` 的 `model_info`：input 1e-7、output 2e-7（每 token，local-cheap），
local-primary 贵 10 倍。但配置里写得很明确，这两条是 W5 D3 给 `openai/fake-model` 演示成本面板用的，
**不参与业务路由**，不是 primary 实际模型的单价。所以这里不把它当账单。

只作量级参考：若套用 local-cheap 单价，每次判定约 3.1e-5、一次结构化回答两次判定约 6.2e-5；
套 local-primary 则各贵 10 倍。要算真钱，得先拿到 primary 模型的官方单价，再乘上表的 token 数。
本轮能确定的结论是**开了开关会多两次短调用、约 513 tokens**，与单价无关。

## 五、容器连真实上游的完整链路

之前只跑过本地判定和单测，这次在容器里把整条链路接通了。关键一步是把 `.env` 里的上游地址
换成 `host.docker.internal`（容器内 `127.0.0.1` 指向容器自己，D1 踩过同一个坑），
再以 `LLM_MODE=openai`、`OUTPUT_GUARD_ENABLED=1`、`OUTPUT_GUARD_MODEL_JUDGE_ENABLED=1` 起容器。

带 `context` 的结构化请求返回 HTTP 200，`upstream_mode=openai`，并且 `output_guard` 里是真实判定：

```json
{"degraded":true,"repaired":true,"toxicity_status":"allow",
 "grounding_status":"unsupported","reasons":["unsupported_claim"]}
```

生成回答先修了一次格式，毒性判定放行，资料依据判定认为回答里的说法在给定资料里找不到根据，
于是返回固定兜底。容器内直接调四个判定（allow / block / supported / unsupported）也全部正确。

端到端计时（各一次，同镜像同请求）：

| 配置 | 完整往返 |
| --- | --- |
| 判定开关开（2 次判定） | 29.630s |
| 判定开关关（基线） | 15.260s |

这组差值 **不能全算成判定器开销**：两次请求都由真实模型生成，生成耗时本身波动就大（开启那次响应体里
`latency_ms` 是 11557.5ms，只算生成与格式修复）。更可靠的口径是上一节的单次判定 P50 × 2。
这里保留数字，是为了说明「开开关后 /chat 会明显变慢」这个方向，不用于精确归因。

## 六、边界与建议

- 30 条是演示规模，`0/10 误拦`不等于生产误拦率 0。样本分布也是刻意挑的难例，不代表线上真实流量。
- 上游偶发超时：修后 20 秒超时下仍有 2/30 失败，生产里会 fail-closed 兜底。首轮 60 秒超时 × 3 次重试时，
  单条最慢 162.8 秒，这个尾部延迟不可接受。
- 判定器是通用大模型加提示词，不是专用分类器；换模型要重跑这套样本，格式毛病可能变样。
- 资料依据判定依赖调用方传 `context`，没传就是 `not_checked`，不算通过。
- **建议继续默认关闭** `OUTPUT_GUARD_MODEL_JUDGE_ENABLED`。要默认打开，至少先做三件事：
  两次判定并发而不是串行、给判定单独设更短的超时和明确的超时降级策略、把 fail-closed 率接进监控。
  另外可以换用输出更稳的模型或改成 structured 输出模式，从源头减少重复 JSON。
